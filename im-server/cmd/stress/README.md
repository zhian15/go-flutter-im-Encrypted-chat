# IM 消息链路压力测试工具

独立验证消息链路的四条性质 —— **不丢 / 不重 / 不乱 / 不卡** —— 尤其在 2000+ 人群这种扇出量级下。

## 为什么需要它

服务端不丢消息这件事，不能靠"改代码的人自己说"来证明。这个工具的价值在于它是**外部视角**：

- 它**不复用被测代码的业务逻辑**（唯一例外是 `internal/pkg/jwt`，只为离线签发令牌、免去上千次登录），所有观测都走公开 HTTP API + WebSocket，与真实客户端同一条路径；
- 它同时用**两条互不相关的证据链**做交叉验证：WS 推送（最后一公里）和 `/message/sync`（服务端从 MongoDB 按 seq 读出的权威序列）。两者对比能直接定位责任方 —— WS 少收但 sync 一条不缺，就是推送丢了；sync 里也缺，那才是链路真丢。

## 快速开始

```bash
cd im-server

# 1) 造靶场：2000 个账号 + 一个 2000 人群（结果落盘，后续反复复用）
go run ./cmd/stress seed -users 2000 -session stress.json

# 2) 端到端压测：2000 个客户端在线收流，20 个发送者打 50 msg/s，跑 60s
go run ./cmd/stress wsload -session stress.json -clients 2000 -senders 20 -rate 50 -duration 60s

# 2b) 用户诉求场景：2000 个客户端各自也发消息（每人 0.1 msg/s，总报价 ≈ 200 msg/s）
go run ./cmd/stress wsload -session stress.json -clients 2000 -each-sends 0.1 -duration 60s

# 3) 一致性校验：确认服务端序列本身自洽（不丢/不重/不乱）
go run ./cmd/stress check -session stress.json

# 4) 判断「踢掉慢客户端」是否可以安全开启
go run ./cmd/stress slowclient -session stress.json -clients 20 -slow 3
```

> 需要本地同时跑 `cmd/api`（HTTP :8080）和 `cmd/gateway`（WS :8080）。地址不同就用 `-base` / `-ws` 覆盖。

## 子命令

### `seed` —— 造靶场

创建 N 个账号，再建一个装着他们的群，把 `{账号 ID, token}` 落盘成会话文件（权限 0600，里面有可直接冒充用户的凭据）。

| 参数 | 默认 | 说明 |
|---|---|---|
| `-users` | 2000 | 账号数（= 群成员数） |
| `-password` | `Stress@12345` | 账号密码 |
| `-group-name` | 压测群 | 群名称 |
| `-session` | `stress-session.json` | 会话文件路径 |
| `-reuse` | true | 已有会话文件且账号数够用就直接复用，不重复注册 |
| `-chunk` | 200 | 邀请成员的分批大小 |
| `-conc` | 16 | 注册并发度（注册有 IP 级限流，别开太大） |
| `-base` / `-ws` | :8080 | API / WS 基址 |
| `-run-id` | 时间戳 | 批次标识，用于生成账号名 |

**注册回落**：注册接口在 `AUTH_MODE=sms/email` 时会要求验证码，脚本拿不到。此时工具自动回落到**游客注册**（按 `deviceId` 幂等，重复调用复用同一账号），因此不影响靶场建立。若两条路都失败，会打印服务端返回的原始错误码与文案。

**撞群上限**：如果服务端 `group_max_members` 限制了规模，工具会精确告诉你"从第几个人开始装不下"，并提示该把配置调到多大。

### `send` —— 纯 HTTP 发送压测

不建 WS 连接，只测「客户端 → 服务端 → 落库」这一段。与 `wsload` 的端到端口径互补：**如果 `send` 很快但 `wsload` 端到端延迟很高，瓶颈就在扇出/推送侧而不是写入侧** —— 这个区分决定了该去优化哪一段。

| 参数 | 默认 | 说明 |
|---|---|---|
| `-senders` | 20 | 发送者数量 |
| `-rate` | 50 | 聚合目标速率 msg/s |
| `-duration` | 60s | 持续时间 |
| `-max-lat` | 30000 | 延迟直方图上限（毫秒） |
| `-json` | — | 结果另存为 JSON，便于两次运行 diff |

输出：尝试数 / 成功数 / **失败码分布** / 实际吞吐 / p50 p90 p99 max avg。

### `wsload` —— 【核心】端到端压测

N 个 WebSocket 客户端连上并持续收流，同时打发送流量，逐条统计。发送侧有两种模式：

- **发送者池模式**（默认）：少数「发送者」用 `-senders` 指定的 token 代发，接收端纯收。
- **每客户端自发模式**（`-each-sends > 0`）：**每个已连接的客户端自己也在发消息** ——
  一个客户端 = 一个真实用户，既收也发。这才是「群里 N 个人同时在发信息」的模拟。

| 参数 | 默认 | 说明 |
|---|---|---|
| `-clients` | 2000 | 接收端连接数（each-sends 模式下也是发送者数） |
| `-senders` | 20 | 发送者数量（仅发送者池模式；与 `-each-sends` 互斥） |
| `-rate` | 50 | 聚合目标速率 msg/s（仅发送者池模式；each-sends 模式下忽略） |
| `-each-sends` | 0 | 每个已连接客户端自己的发送速率 msg/s；`>0` 启用每客户端自发模式 |
| `-duration` | 60s | 持续时间 |
| `-rampup` | 2ms | 每个连接的拨号间隔（避免瞬时打爆 accept 队列） |
| `-grace` | 3s | 停发后等待在途消息的时间 |
| `-timeout` | 15s | 单次 HTTP 超时 |
| `-json` | — | 结果另存为 JSON |

#### 每客户端自发模式（`-each-sends`）—— 模拟「群里 N 个人同时发消息」

```bash
# 2000 个用户连上，每人自己以 0.1 msg/s 发送（约每 10 秒 1 条），总报价速率 ≈ 200 msg/s
go run ./cmd/stress wsload -session stress.json -clients 2000 -each-sends 0.1 -duration 60s
```

语义与约束：

- 第 i 个客户端用 `sess.Users[i]` 的 token 发送 —— **与它自己那条 WS 连接是同一个用户**，
  不会张冠李戴（这是"模拟真人"的关键）。
- 总报价速率 = `clients × each-sends`。
- `-each-sends > 0` 时**忽略 `-senders` 发送者池**；若同时显式传了 `-senders`，工具会
  **直接报错要求二选一**（两者都有默认值，静默取舍太容易误用）。同时 `-rate` 也被忽略。
- 若 `-clients` 超过靶场账号数，会明确提示"需要 N 个账号，靶场只有 M 个，先 seed 更多"。

**端到端延迟怎么测的**：发送时把时间戳和「全局唯一槽位」编码进消息 `content`，接收端收到后自行相减。**不需要改服务端埋点**，也就不存在"指标本身被改坏"的可能。

**关于槽位与内存**：每个发送动作先从一个全局 `atomic.Int64` 取一个全局唯一槽位（0 起），再写进 payload 的 `i` 字段；同时带上本次运行的标识 `r`（`runStamp`，用于排除上一次跑的残留消息）。位图只按"总消息量"预分配（`预期总量 × 1.2 + 10000`），**与发送者数量解耦** —— 否则 2000 个发送者时按"发送者数 × 每发送者容量"预分配会瞬间吃掉几百 MB。若极少数样本超出槽位容量，工具会累加 `droppedSamples` **并在报告里打印**，绝不静默丢弃（静默丢样本会让"丢失率"失真）。

输出包括：连接成功率、发送失败码分布、**丢失条次与丢失率**、重复条次、乱序条次、端到端延迟分位、每个客户端收到条数的最小/最大值，以及三项用户维度指标：

- **成功发出消息的用户数**（`distinctSendersOK` / 参与发送的用户数）—— 直接回答"N 人里到底几人发得出去"；
- **报价速率 vs 实际达成速率**；
- **发送延迟分位**（各用户聚合）。

最后那几项是刻意做的：聚合丢失率可能很好看（0.1%），但如果有 50 个客户端被彻底饿死、或只有 3 个人真发出了消息，真实用户感受就是"我发不出去 / 我收不到消息"。只看平均值的压测会漏掉这个。

### `slowclient` —— 慢客户端回归

**这是"能不能开 `KICK_SLOW_CLIENTS` 开关"的决策实验。**

踢连接本身是安全的，前提是客户端重连后能靠补拉把消息全捞回来。这个子命令在同一个进程里把整件事走一遍：

1. 挂若干个**从不读 socket** 的客户端，把它的 TCP 缓冲堵死 —— 这是唯一能真实触达"服务端写不动"这个分支的办法；
2. 正常发送压测流量；
3. 关掉慢客户端 → 重新连一条 WS → 用 `/message/sync` 从 seq 0 全量拉回；
4. 比对"补拉捞回多少"与"发送成功多少"，给出**补拉覆盖率**。

覆盖率 100% = 可以放心开踢连接开关；不足 100% = 开了就会真丢消息。

| 参数 | 默认 | 说明 |
|---|---|---|
| `-clients` | 20 | 正常接收端数量 |
| `-slow` | 3 | 慢客户端数量（从不读 socket） |
| `-senders` / `-rate` / `-duration` | 4 / 20 / 20s | 发送侧参数 |

> 说明：`slowclient` **不提供 `-each-sends`**。它的目的只是判定"断线重连后补拉能否零丢失"，
> 与"多少用户同时在发"这一维度无关；保持单一发送者池能让该决策实验的结论更干净、更易复现。
> 需要模拟多用户并发发送时，请用 `wsload -each-sends`。

#### 为什么每轮都必须区分 `runStamp`（一个曾经的"假全绿"缺陷）

`slowclient` 用 `/message/sync` 从 `afterSeq=0` **全量**补拉，而会话 ID 在多次运行间复用
（它写在 `stress-session.json` 里）、槽位 `i` 每次都从 0 重新计数。若消息不带"运行标识"，
**上一次跑留在同一个群里的残留消息会与本次的槽位号完全重合**，被算作"本次补回" ——
于是即使本轮消息**全部真丢**，工具也会打印 `补拉覆盖率 100%`、并给出"开启
`KICK_SLOW_CLIENTS` 是安全的"。这是**危险方向的假全绿**。

修复：payload 增加 `r` 字段（`runStamp`），接收端与补拉比对都**强制按 `runStamp` 过滤**；
旧格式消息解码后 `r == 0`，永远不会等于真实 `runStamp`，被稳定排除。此外：
- 当本轮**发送成功 0 条**（2000 人同群时极易被 per-conv 限流全部拦截），
  补拉实验直接判为**「不可结论」**，不再打印"安全开启"的空跑绿。

**回归防护**：`recovery_test.go` 用纯逻辑（无需服务端）证明了污染会被排除 ——
`go test ./cmd/stress/ -run MatchRecovered -v`。其中 `TestMatchRecoveredExcludesPreviousRun`
同时复刻了"修复前"的行为作对照：旧逻辑 `matched=10`（覆盖率 100%，假全绿），
修复后 `matched=0`（覆盖率 0%，真实反映丢失）。

**真机复现配方**（同一群里连续跑两次，验证第二次不会被第一次抬高）：

```bash
# 第 1 次
go run ./cmd/stress slowclient -session stress.json -clients 20 -slow 3 -senders 4 -rate 20 -duration 20s -json sc-1.json
# 第 2 次（参数完全相同）
go run ./cmd/stress slowclient -session stress.json -clients 20 -slow 3 -senders 4 -rate 20 -duration 20s -json sc-2.json
```

两次输出的「补拉覆盖率」应**相互独立、量级一致**（第二次不得因第一次的残留消息而虚高）。
每次报告都会打印本轮的 `runStamp` 与「发送成功 N 条」，可据此核对覆盖率分母是否可信。

### `check` —— 独立一致性校验

把服务端的权威序列整段 drain 下来，直接检查它自身是否自洽：seq 有没有**空洞**（丢）、有没有**重复**（重）、返回顺序有没有**回退**（乱）。

不依赖任何客户端行为，因此可以当**仲裁者**：当 `wsload` 报丢包时，跑一次 `check` 就能判定到底是推送丢还是链路真丢。

| 参数 | 默认 | 说明 |
|---|---|---|
| `-conv` | 会话文件里的值 | 会话 ID |
| `-from-seq` | 0 | 起始 seq（0 = 全量） |
| `-max-pages` | 500 | 最多翻页数（500 × 500 = 25 万条） |

**注意**：seq 空洞不一定等于丢消息 —— 后台被"屏蔽"的消息在 sync 里本就不下发，也会形成空洞。要严格区分需对照 MongoDB 里该会话的实际文档数。工具的措辞是"存疑"，不会替你下结论。

### `stats` —— 运维指标

打印 `/health` 与 `/ws/stats`。跑压测前后各执行一次，**看差值判断消息丢在哪一层**：

| 指标变化 | 含义 |
|---|---|
| `droppedFrames` 增长 | WS 写缓冲塞不下被丢帧（慢客户端 / 带宽问题） |
| `droppedEvents` 增长 | 事件消费侧被丢（Redis PubSub 缓冲打满，扇出跟不上） |
| 两者都不涨却仍丢消息 | 问题在**客户端补拉**，不在服务端推送 |

三种根因的处理方式完全不同，所以这个区分很关键。

## 重要的前提：发送限流（也是 2000 人同群发送的硬瓶颈）

服务端对 `/message/send` 有两级限流（`internal/middleware/ratelimit.go`）：

- **per-user 20 msg/s**（突发 50）
- **per-conversation 5 msg/s**（突发 20）

> **结论（务必先读）**：服务端 **per-conversation 限流 = 5 msg/s（突发 20）**。所以当
> 2000 个用户**同处一个群**里发送时，瓶颈**必然是这条限流** —— 而不是链路吞吐能力。
> 无论连接、扇出、存储多快，这个群的发送上限就是约 5 msg/s（超出部分返回 `429`）。
> 这是**产品级决策点**：要么调高 per-conv 阈值，要么把群拆小 / 按会话分区后分压。
> 因此"2000 人同群发送"的压测，测的是**限流与退避行为**，而不是"链路能扛多少吞吐"。

`429` 是**预期行为，不是故障**。工具会把 429 单独归类并高亮占比，不会把它算进"丢消息"。要做超高吞吐压测，必须把流量分散到多个会话（多建几个群）。

被限流也不必担心消息重复：`clientMsgId` 是幂等的，客户端退避后重发是安全的。

## 2000 人基线场景与通过标准

### 场景 A：少数发送者代发（测链路吞吐）

```bash
# 靶场
go run ./cmd/stress seed -users 2000 -session stress.json

# 跑前基线
go run ./cmd/stress stats -session stress.json

# 逐级加压（每级之间跑一次 check 确认序列自洽）
for r in 5 20 50 100; do
  go run ./cmd/stress wsload -session stress.json -clients 2000 -senders 20 -rate $r -duration 60s -json run-$r.json
done

# 跑后对比 + 一致性校验
go run ./cmd/stress stats -session stress.json
go run ./cmd/stress check -session stress.json
```

### 场景 B：【用户诉求】2000 人同时在同一个群里发消息

```bash
# 1) 造靶场：2000 账号 + 一个 2000 人群
go run ./cmd/stress seed -users 2000 -session stress.json

# 2) 跑前基线
go run ./cmd/stress stats -session stress.json

# 3) 2000 个客户端连上，每人自己以 0.1 msg/s 发送（总报价 ≈ 200 msg/s，跑 60s）
go run ./cmd/stress wsload -session stress.json -clients 2000 -each-sends 0.1 -duration 60s -json each.json

# 4) 一致性校验（仲裁者：区分"推送丢"还是"链路真丢"）
go run ./cmd/stress check -session stress.json

# 5) 跑后对比
go run ./cmd/stress stats -session stress.json
```

**判读方法（场景 B）**：

1. 先看**「成功发出消息的用户数」**：`distinctSendersOK / 2000`。这是"2000 人里到底几人
   真发得出去"的直接答案。若远小于 2000，说明大多数用户被限流/退避压住了。
2. 看**限流占比**：因为报价速率（≈200 msg/s）远超单会话 5 msg/s，**必然出现大量 429**。
   这**不是故障**，而是 per-conv 限流在生效（见上文结论）。
3. 看**实际达成速率 vs 报价速率**：实际应被压到 ≈ 单会话上限附近（含突发余量），
   与报价的差距即"产品级限流造成的吞吐上限"。
4. 再看**不丢/不重/不乱**：真正要验证的是"**发送成功的那部分**是否 100% 送达"。
   只要"丢失 = 0、重复 = 0、乱序 = 0"，说明链路本身可靠；429 的部分不算丢消息。
5. 若要让 2000 人都能畅快发送，**必须改服务端 per-conv 阈值，或把大群拆成多个小群**再分压，
   否则这条限流永远是最先撞到的墙。

**通过标准**（工具会自己在末尾打印判定）：

| 性质 | 标准 |
|---|---|
| 不丢 | 丢失 = 0 条次；单客户端收到条数的最小值 = 应送达条数 |
| 不重 | 重复 = 0 条次 |
| 不乱 | 乱序 = 0 条次 |
| 不卡 | 端到端 p99 在几百毫秒内（不做硬判定，超 1000ms 会提示"关注"） |
| 不饿死 | 最少收到数 == 应送达数（否则有客户端被饿死） |
| 样本完整 | `droppedSamples == 0`（有值说明槽位越界，丢失率可能失真） |

`-rate` 超过 5、或 each-sends 模式下的报价速率超过 5 时都会开始出现 429，这是限流生效的正常表现。**真正要看的是"发送成功的那部分是否 100% 送达"**，而不是"我发了多少"。

## 已知限制

- **会污染目标数据**：工具会真的往目标群里写消息（内容是一段 JSON）。**只在独立测试环境跑**，不要对着生产群压测。
- **延迟依赖时钟**：发送端与接收端在同一进程，所以端到端延迟是准的；如果拆成两台机器跑，时钟偏差会直接计入延迟。
- **`seed` 会创建真实账号**：账号名形如 `stress_<批次>_<序号>`，密码统一。清理需要走后台用户管理或直接清库。
- **Linux 上的连接数上限**：单进程 2000 条 WS 连接需要足够的文件描述符，通常要 `ulimit -n 65535`。
- **`-each-sends` 会为每个客户端额外起一个发送 goroutine**：2000 客户端时约 4000 个 goroutine（收 + 发），本机 CPU/时钟精度不足时测出的延迟会包含客户端自身调度延迟。极端规模建议把发送端与接收端分开跑。
- **本工具不做性能优化承诺**：它自己是压测客户端，若在 2000 客户端收流的同时本机 CPU 打满，测出的延迟会包含客户端自身的调度延迟。极端情况下建议把发送端与接收端分开跑。

|---|---|
| `main.go` | 响应信封、HTTP 客户端、会话文件、统计与位图工具、入口分发 |
| `seed.go` | 靶场建设（注册 + 建群 + 分批邀请） |
| `load.go` | `send` / `wsload` / `slowclient` 与压测引擎 |
| `check.go` | `/message/sync` drain、一致性校验、运维指标 |
| `recovery_test.go` | 补拉覆盖率实验的回归防护：证明上一次跑的残留消息会被 `runStamp` 排除 |
